# Community Service Visual Design Skill — Iteration Log

## 当前版本
V1.0

## 版本阶段
从 v0.x 试验性迭代进入 V1.x 架构级迭代

---

# 一、项目最初目标

项目最初希望解决的问题是：

如何把“社区公共服务信息”转化为一个可复用的 AI Agent Skill，使 Agent 不只是生成一张图，而是能够复现设计师完成社区海报时的：

- 任务理解；
- 信息筛选；
- 文案整理；
- 视觉方向探索；
- 人工审查；
- 图像处理；
- 文字排版；
- 最终交付。

课程目标不是单纯生成海报，而是：

将设计专业知识固化成可重复执行、具有边界、可检查、可验证的工作流。

---

# 二、早期核心问题

项目最早版本暴露的问题包括：

- Human Gate 会被跳过；
- 输出格式不稳定；
- 要 PNG 时可能只得到 PDF；
- 输入信息少时 Agent 会留下空白占位；
- Agent 不会主动补充可合理生成的公众传播文案；
- 海报结果更像说明页；
- 用户无法只通过文字描述判断视觉方向；
- 场景图片与任务不匹配时缺少处理机制；
- 同一张社区白天图被反复使用；
- Agent 容易产生科研风、PPT 风和卡片堆砌。

这些问题推动了 v0.x 的连续迭代。

---

# 三、v0.1 — 基础 Human Gate 与信息安全

## 主要目标

让 Agent：

- 不直接跳到最终图；
- 区分可生成内容和不可虚构事实；
- 保证 PNG 最终交付；
- 先确认信息，再设计。

## 主要修改

建立三个 Human Gate：

- Gate 01：内容确认；
- Gate 02：视觉方向；
- Gate 03：最终审查。

同时将输入区分为：

### 可主动生成

例如：

- 一般性公众提醒；
- 行动建议；
- 副标题；
- 传播短句；
- 模块标题。

### 不得虚构

例如：

- 时间；
- 地点；
- 电话；
- 机构；
- 人名；
- 网址；
- 二维码指向。

## 发现的新问题

Gate 02 仍然只是文字方向。

用户无法直观看到方向差异。

---

# 四、v0.2 — Gate 02 视觉化

## 主要修改

要求 Gate 02 不再只输出文字。

必须生成：

- 3 个不同方向；
- 3 张低保真 PNG；
- 必要时并排比较。

## 测试任务

“社区便民维修与旧物交换日”。

## 测试结果

工作流可以跑通。

但方向图出现：

- 科研风；
- 信息板感；
- 图片占比小；
- 标题不够大胆；
- 色彩较保守。

用户需要手动告诉 Codex：

- 更参考 style；
- 增加图片比例；
- 颜色更跳；
- 标题更大；
- 更有社区氛围。

这些人工纠偏后来被继续写回 Skill。

# 五、v0.3 — 社区亲和与资源系统

## 主要目标

把人工视觉纠偏变成默认规则。

## 新增

- 默认社区亲和；
- 避免科研风；
- style 参考提高优先级；
- fonts / icons / logos / templates；
- raw-task；
- 自动 Brief 草案；
- README；
- Codex 启动提示。

## 用户反馈

用户提出：

老师最终测试不一定会给标准 Brief。

因此 Skill 必须支持：

自然语言任务 → Agent 自动整理 Brief。

这为后续“对话输入优先”埋下基础。

---

# 六、v0.4 — 场景图适配机制

## 主要问题

此前工作流过度依赖固定社区图。

新的问题包括：

- 白天社区图能否用于夜间活动？
- 晴天图能否用于暴雨 / 阴雨主题？
- 没有图怎么办？
- 图片与任务语义不符怎么办？

## 修改

增加图片适配判断：

- A：直接适合；
- B：可受控修改；
- C：不适合。

允许修改：

- 白天 → 夜晚；
- 晴天 → 阴雨；
- 色温；
- 光照；
- 饱和度。

同时强调：

不得无理由改变空间结构。

---

# 七、v0.5 — Theme Semantic Elements

## 背景

用户发现：

仅改变照片天气 / 日夜并不能总是表达活动主题。

例如：

夜间电影活动仅有夜景仍不够“电影”。

## 新增

主题语义元素 Level：

- Level 0：不加；
- Level 1：少量高价值元素；
- Level 2：有限主题系统。

例如：

电影夜可以加入：

- 幕布；
- 星点；
- 灯串。

但用户可以明确拒绝。

之后 Agent 不得偷偷重新加入。

---

# 八、v0.5 综合测试：社区星空电影夜

该测试成为一次重要验证。

## 成功点

Agent 能：

- 从 raw-task 整理内容；
- 分析白天场景图；
- 改成夜景；
- 加入主题语义元素；
- 停在 Gate；
- 生成三种低保真方向；
- 生成中英文正式稿。

## 用户人工修改

用户进一步要求：

- 色彩更有层次；
- 字体不要太僵硬；
- 主标题不要一味超粗；
- 电影幕布要进入真实场景关系；
- 灯串与支撑结构增加场景可信度。

## 阶段判断

工作流本身已经较稳定。

主要问题开始从：

“Agent 会不会执行流程”

转向：

“Agent 默认会做成什么审美”。

`visual-preferences.md`

Noto 不是任务依赖。

# 十、v0.6 → v0.7：艺术字与高饱和配色

## 字体新反馈

用户希望允许 Agent：

- 不完全依赖字体库；
- 可以生成图片形式艺术字。

由此增加：

- 短主标题可艺术化；
- 优先真实文字路径化；
- 生成式艺术字必须逐字校对；
- 时间、电话、地点等不得使用不可靠的生成式文字。

## 配色新反馈

用户提供新的海报参考后指出：

之前结果：

- 饱和度偏低；
- 色相距离近；
- 不够跳跃；
- 缺少舒适的现代高饱和感。

用户还提出：

场景图本身也可以：

- 调色；
- 压暗；
- 提亮；
- 改色相；
- 降杂色；

以服务文字对比。

# 十二、v0.7 测试：社区草地音乐野餐日

该测试采用：

- 无正式 Brief；
- raw-task；
- 极短 Codex 启动提示。

目的是验证：

Skill 是否真的能够脱离复杂启动提示自己运行。

## 结果

流程仍可运行。

但 Gate 02 暴露明显视觉问题：

### 1. 三个方向名义不同，骨架相同

常见结构：

- 顶部标题；
- 中间完整矩形照片；
- 底部大块说明。

### 2. 信息分区明显

仍然像：

“设计过的社区公告”。

### 3. 配色仍然偏保守

即使出现蓝、绿、橙等颜色：

整体色相关系仍安全。

### 4. 场景图仍作为矩形内容模块

没有真正成为：

- 背景；
- 出血图；
- 叠层；
- 主视觉。

# 十三、v0.8 — 构图家族与 Graphic Poster Mode

## 主要修改

Gate 02 从“风格名”升级为“构图家族”。

包括：

- Typography Poster；
- Hero Background Poster；

- 顶部标题；

- 底部说明；

- 圆；
- 星；
- 箭头；
- 路径；
- ICON；
- 简化人物；
- 简化建筑；
- 大标题。

## 多图模式

开始讨论：

- Hero Image；
- Supporting Images；
- 拼贴；
- 胶片；
- 图形蒙版。

# 十四、style 文件夹优化

用户最初在 style 中放了约 9 张参考图。

Gate 02 的运行时间明显变长。

用户怀疑：

- 网络；
- 模型负载；
- 或参考图数量过多。

无法确认具体原因。

但从 Skill 结构角度判断：

9 张图会增加：

- 视觉分析量；
- 上下文；
- 风格协调成本；
- 审美平均化风险。

## 最初方案

曾建议把 style 分成：

- color；
- composition；
- typography；
- graphic-language。

## 用户反馈

用户明确指出：

真实参考图通常同时包含：

- 配色；
- 构图；
- 字体；
- 图片处理；

很难严格分类。

用户不希望为了 Skill 改变自己的灵感图管理方式。

## 最终修改

style 变成：

整体视觉参考池。

只建议用户：

自行删减到 4–5 张最喜欢的图。

不再要求：

- 分类；
- 特殊命名；
- 单图单功能。

Agent 负责综合提炼。

---

# 十五、测试其他人的 Skill

用户收到另一套社区海报 Skill 根目录，希望用自己的 Codex 测试。

测试后反馈：

## 可用点

该 Skill：

- 信息确认后可以直接生成图片；
- 艺术感较强；
- 不需要像当前 Skill 一样经过较多中间版式 / PDF 约束；
- 能根据不同社区服务场景调用对应参考图片；
- 服务类型变化时，排版思路也会变化。

## 不足或不适合直接照搬的部分

该 Skill 的交互更偏：

每次只问一个问题。

用户认为：

虽然清晰，但会：

- 拉长任务时间；
- 交互轮数过多。

另外：

直接让图像生成承担所有文字：

虽然艺术感强，

但对于：

- 电话；
- 时间；
- 地址；
- 中文小字

准确性风险较高。

因此决定：

不直接替换现有 Skill。

而是：

以本项目原 Skill 为主，吸收其运行优点。

这成为从 v0.x 升级到 V1.x 的主要原因。

# 十六、为什么从 v0.8 直接进入 V1.0

这次修改已经不是继续增加一条视觉规则。

而是同时改变：

- 用户输入方式；
- Gate 01 交互方式；
- 场景参考机制；
- 任务状态管理；
- 图片上传流程；
- 配色决策流程；
- 图像生成与精确排版关系。

因此不再使用 v0.9。

正式进入：

V1.0。

# 十七、V1.0 架构升级 1：Conversation First

## 旧逻辑

用户需要自己理解：

- raw-task 放哪里；
- brief 放哪里；
- 社区场景图放哪里。

## 用户反馈

用户认为这对普通使用者过于繁琐。

如果是一个真正可复用 Skill：

用户不应该先学习项目文件结构。

## V1.0 修改

默认从对话输入开始。

例如：

“做一个社区宠物友好日海报。”

Agent 自动识别已有信息。

用户只在 Gate 中：

- 点击；
- 填写；
- 上传图片。

文件系统退到后台。

# 十八、V1.0 架构升级 2：Gate 01 从报告变成动态问卷

## v0.x 的问题

Gate 01 输出越来越长。

包含：

- 已知信息；
- AI 建议；
- 缺失事实；
- 场景图分析；
- 配色；
- 语义元素；
- 视觉路线；
- 图像处理建议。

用户必须：

阅读整篇报告，再逐项回复。

测试反馈认为：

交互复杂、难理解。

## 用户提出的新目标

Gate 01 应类似：

“问卷星”。

用户希望：

- 鼠标点击；
- 单选；
- 多选；
- 输入框；
- 图片上传；
- 推荐选项。

而不是：

看完选项编号，再键入“A / B / C”。

## V1.0 方案

优先使用：

原生可点击 UI。

若环境不支持：

生成 HTML 表单。

只有前两种都不可用时：

才退回结构化文本问卷。

---

# 十九、V1.0 Gate 01 不再一次收齐所有信息

这是用户进一步强调的新要求。

## 不希望出现

用户填完一个大表单后：

Agent 就假设所有问题都解决，然后直接继续工作。

## 希望采用

分阶段、动态分支。

因此 Gate 01 被拆成：

- Gate 01.1A；
- Gate 01.1B；
- Gate 01.2。

但它们仍属于同一个 Human Gate。

不会增加第四个 Human Gate。

# 二十、Gate 01.1A — 基础事实

只收集：

- 主题；
- 受众；
- 时间；
- 地点；
- 报名；
- 联系方式；
- 输出规格；
- 是否准备上传图片。

这一阶段：

只问事实。

不提前讨论：

- 图片怎么改；
- 图片适不适合；
- 是否改夜景；
- 配色；
- 拼贴；
- 视觉路线。

## 原因

例如：

用户刚说：

“我要上传 1 张场景图。”

此时 Agent 还没有真正看到图片。

提前问：

“要不要压暗 / 改夜景 / 风格化？”

缺乏依据。

因此：

图片真正上传后，才进入下一步判断。

---

# 二十一、Gate 01.1B — 中英文案确认

用户进一步指出：

Gate 01 不能只确认事实。

本项目原来最大的优势之一：

就是对文字和信息更可控。

因此 V1.0 必须保留：

中英文案确认。

## 工作方式

基础事实足够后：

Agent 自动生成：

- 中文案；
- 英文案（如任务需要）。

然后提供选择：

- 全部确认；
- 中文修改；
- 英文修改；
- 再精简；
- 更有传播感；
- 自定义修改。

## 重要规则

中英文案未确认前：

不得进入 Gate 01.2。

## 为什么重要

如果先做视觉：

后面主标题长度、英文长度、服务项目数量一改：

版式会大幅返工。

因此文案先锁定，再设计。

---

# 二十二、Gate 01.2 — 图片、配色与视觉

文案确认后：

才进入真正视觉决策。

## 0 张图

默认：

Graphic Poster Mode。

## 1 张图

图片上传后：

先判断：

- 语义；
- 构图；
- 留白；
- 是否适合 Hero。

然后再问用户：

- 是否允许调色；
- 是否允许裁切；
- 是否允许风格化；
- 是否允许日夜 / 天气变化。

## 多张图

先分析：

- 推荐主图；
- 推荐附图。

再让用户选择：

- Hero + Supporting；
- 拼贴；
- 胶片；
- 多窗格；
- 仅主图。

---

# 二十三、V1.0 配色改为用户在 Gate 01.2 选择

此前 visual-preferences 中逐渐积累了具体颜色组合。

用户进一步提出：

最终配色仍然应该由用户在 Gate 01 选择。

## 新规则

Agent 根据：

- 当前任务；
- 服务类别；
- 场景参考；
- 图片；
- style；

动态生成 3–4 个配色方向。

用户点击选择。

## visual-preferences 的变化

不再长期固定：

某任务一定蓝黄；
某任务一定绿白。

而只固定：

- 高饱和倾向；
- 跳色；
- 现代；
- 舒适；
- 避免科研灰蓝。

具体色相由任务决定。

---

# 二十四、V1.0 场景参考库

从其他 Skill 的测试中吸收一个重要机制：

根据服务场景选择不同参考。

新增建议目录：

- 健康义诊；
- 老年关怀；
- 儿童教育；
- 政策宣传；
- 社区活动；
- 环境保护；
- 志愿服务；
- 应急服务；
- 通用。

## 与 style 的区别

### style
用户长期审美。

### scenarios
具体服务类别的视觉语气与信息组织。

二者同时使用。

## 不照搬的内容

不把：

“应急 = 红色”
“环保 = 绿色”
“老年 = 橙色”

写死。

场景路由影响：

- 信息组织；
- 构图语言；
- 图形表达；
- 视觉语气。

配色仍在 Gate 01.2 动态决定。

---

# 二十五、V1.0 新的渲染问题

对比其他 Skill 后发现：

直接图像生成的优势：

- 整体感强；
- 艺术感强；
- 边框、标题、图形统一。

本项目旧方式的优势：

- 文字准确；
- 时间 / 电话可靠；
- 可控；
- 双语稳定。

但用户指出：

如果简单采用：

“生成图一半 + PDF 文字一半”

会产生新的割裂。

---

# 二十六、用户提出的典型割裂案例

例如：

- 一个气泡外框由图像生成；
- 气泡具有手绘、艺术化视觉；
- 气泡里的小标题却突然使用普通微软雅黑。

结果：

视觉上像：

后贴文字。

同样：

- 大标题非常艺术；
- 底部信息区完全像 Word；

也会破坏整体海报感。

因此：

不能简单以“图片 / 文字”切分页面。

---

# 二十七、V1.0 架构升级 3：Component Integrity

正式引入：

组件完整性原则。

## 核心思想

一个视觉组件尽量由同一种设计逻辑完成。

例如：

气泡应同时考虑：

- 轮廓；
- 底色；
- 图标；
- 标题；
- 正文。

如果文字需要精确：

可将整个组件：

在 SVG / HTML / Canvas 中统一设计。

而不是：

只把文字后贴到生成图上。

# 二十八、V1.0 文本三分类

## Type A：关键事实

包括：

- 时间；
- 电话；
- 日期；
- 地址；
- 机构；
- 报名方式；
- 二维码说明；
- 网址。

必须精确。

## Type B：结构信息

包括：

- 活动亮点；
- 模块标题；
- 服务项目；
- 标签。

根据所在组件决定。

## Type C：表现性文字

包括：

- 主标题；
- 副标题；
- slogan；
- 关键词。

可艺术化。

# 二十九、PDF 在 V1.0 中降级

旧版本中：

PDF / HTML / SVG 可能作为较显眼的中间步骤。

用户新反馈：

过度依赖 PDF 约束：

会削弱图像生成的整体艺术感。

## V1.0 新定义

PDF 只在：

- 打印；
- 矢量；
- 精确版式归档；

时使用。

如果最终任务只要求 PNG：

PDF 不再是默认视觉阶段。

# 三十、Gate 02 在 V1.0 中的定位

Gate 02 保留。

但继续强化：

“看图选择”。

不要求用户阅读长篇方向说明。

必须有：

- A 图；
- B 图；
- C 图。

三图应直接体现：

- 构图差异；
- 色彩差异；
- 图片使用差异；
- 信息密度差异；
- 标题表达差异。

用户主要通过视觉选择。

# 三十一、Gate 03 保留

- 艺术字错误；
- 电话排错；

最终成图检查。

# 三十六、V1.0 当前已知风险

仍需要测试：

## 1. 可点击表单兼容性

不同 Codex / Agent 环境可能对：

- 原生按钮；
- HTML 表单；
- 文件上传交互

支持程度不同。

因此必须保留 fallback。

## 2. Gate 01 是否会变得过碎

虽然不再一次问所有问题：

也要避免：

每个小问题都单独一回合。

目标：

每次 3–6 个同类问题。

## 3. 图像生成文本准确性

主标题艺术化仍可能错字。

必须校对。

## 4. 组件级混合渲染是否稳定

需要测试：

- 精确文字组件；
- 生成式背景；
- 艺术标题；

是否能真正融合。

## 5. 场景参考库是否导致分析变慢

应限制：

每次只读最相关场景。

不要全库扫描。

- 文案确认；
- 配色选择；
- 图片处理权限；
- 人工 Gate；

- 最终审查。
